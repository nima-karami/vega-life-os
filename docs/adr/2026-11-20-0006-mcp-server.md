# ADR 0006 — An MCP server for agents

Date: 2026-11-20
Status: Accepted

## Context

The owner wants their own agents (Claude Code, Codex, Cursor, scheduled agents) to read VEGA and
change it the way they would in the app (card VEG-1). Until now the only write path was the web
app's tRPC client, authenticated by a Firebase ID token that expires within an hour. The server
was a generic CRUD layer, and every domain rule ran only in the web store: the completion stamp,
the habit runway, value and goal cascades, goal progress, the journal merge, one review per
period. An external writer that bypassed the store would have left data the app never produces.

Owner decisions, verbatim from the kickoff: agent power is "Per-token: read or read+write" (bulk
wipe and import stay app-only), and shipping is "PR ready, you merge".

## Decision

- **Endpoint.** `POST /mcp` on the existing `vega-server`. It uses the MCP Streamable HTTP
  transport (`@modelcontextprotocol/sdk` 1.32.2) in stateless JSON mode: a fresh server and
  transport per request, no sessions. It ships with the normal deploy, and there is no new
  service.
- **Auth: personal access tokens.**
  - Minted in Settings through Firebase-authenticated tRPC, so a token can never mint, list or
    revoke tokens.
  - Format `vega_pat_` + 32 random bytes. Only the SHA-256 hash is stored, at
    `accessTokens/{hash}`, a path client rules can't read.
  - Each token has a scope (`read` | `write`) and the owner's IANA time zone.
  - At most 10 active tokens. Every request re-reads the token doc, so a revoke takes effect on
    the next call.
  - OAuth (for claude.ai connectors) is deferred.
- **One implementation of the domain rules.**
  - The pure logic moved from `apps/web` into `packages/shared/src/domain`. The web store and
    the server import the same functions.
  - Time, zone conversion and id generation are explicit parameters. Their defaults reproduce
    the web's old behavior; the server always passes the token owner's clock.
- **Writes are change sets.**
  - Pure planners turn a tool call into an ordered list of puts and removes: children first,
    the target last.
  - Each op carries an expectation: the Firestore `updateTime` it was planned on, or "absent".
    A write that depends on a parent (a task on a goal, a check-in on a habit) carries a
    read-only check of that parent at its planned version.
  - Parent deletes carry dependent-query guards. One-per-key rows (a day's journal, a week's
    review) carry a guard that runs with the write claiming the key.
  - A document other operations check is written in the final chunk, so every earlier chunk
    checks the version the plan read.
  - Each chunk commits in one Firestore transaction that also advances the user's sync counter,
    so committed data always reaches the web poll and a concurrent edit is never overwritten.
  - Cascading deletes need a confirmation digest returned by a preview.
- **Tools.**
  - Five read tools: overview, day, list, get, describe.
  - Generic create, update and delete for every writable collection.
  - Five domain verbs: task status, habit check-in, habit state, subgoals, journal.
  - A read token never sees the write tools.

## Consequences

- An agent's change appears in an open app at its next sync poll (≤ 5 min, or on focus), not
  instantly.
- The signed-out demo sandbox lives in the browser and stays unreachable for agents.
- Profile edits, token expiry, analytics tools and calendar event edits are follow-ups.
- A new domain rule now goes in `packages/shared/src/domain`, with its web caller and the MCP
  planner both using it. Duplicating it on one side would drift.
- Server-generated habit instances use one id per habit slot (`t_<habitId>_<date>`, or a
  hashed `th_…` form for very long habit ids), the same id a check-in claims, so two
  server writers racing for a slot collide instead of duplicating it. The web client still
  generates random ids; a slot it already filled is kept.
- A large write that fails after its first chunk returns the ids it committed and asks the
  agent to re-run, which finishes the job. An agent can see that partial state in between.
